\section{Strategy: vectors, simulation, independent verifier}
\label{sec:verif_strategy}

A cryptographic engine that is verified only against itself proves
nothing: an error in the S-box would be reproduced identically in the
model used to check it. The verification of this work therefore rests on
three legs that do not share an implementation.

\begin{enumerate}
\item \textbf{Official vectors.} Every primitive is checked against the
test vectors published with its standard: FIPS~197 and SP~800-38A for
AES, RFC~4493 and the NIST example file for CMAC, and the CAVP response
files for CTR\_DRBG (with and without derivation function, with and
without reseed). These are known-answer tests and they settle
correctness of the algorithm.
\item \textbf{Independent reference models.} A bit-exact model of the
generator was written in Python with its own AES, derived from the
standard without looking at the VHDL. It is validated against the CAVP
vectors first, and only then used to generate expected values for the
fixed input layout of the hardware and to recompute the tags of the
system-level bench. Two implementations that agree are worth more than
one that passes.
\item \textbf{An independent verifier in the loop.} On hardware the
ESP32 reads the key in test mode and recomputes with mbedtls, and with
its own AES accelerator, the authentication tag of every challenge the
engine answers, so that the final check is performed by a third,
unrelated implementation over a real bus. It has done so on the board:
forty tags out of forty in each of three sessions \meas{}
(Section~\ref{sec:bringup}).
\end{enumerate}

Two working rules apply throughout, both learned in the black-box study
of the ESP32 that opens this work: the output of a compilation, simulation or
measurement is never filtered before being read in full --- a filter
hides exactly the warning that mattered --- and failures are recorded
whole, never discarded. Twice in this work a filter on the simulator's
log hid a result, and both times the fix was to remove the filter.

\section{Reference models in Python}
\label{sec:refmodels}

\texttt{ctr\_drbg\_ref.py} implements AES-128 encryption, the block-cipher
derivation function, CBC-MAC and CTR\_DRBG with and without derivation
function, in pure Python and from the text of SP~800-90A. The AES asserts
the two FIPS~197 vectors at import; the DRBG is exercised against the CAVP
response files following the CAVS procedure (instantiate, optional reseed,
two generate calls, compare the second): \textbf{960 AES-128 cases, all
passing}. One defect was found in the file parser rather than in the
model --- a section header must close the pending test case before the
parameters change, otherwise the last case of every parameter block is
evaluated with the next block's parameters --- and it is worth recording
because its symptom, a single failure at count~14 of each block, looked
exactly like an algorithmic error.

A second script, \texttt{gen\_drbg\_vectores.py}, drives the validated
model through the sequence the hardware supports (instantiate with 48
bytes of entropy and 16 of nonce, generate twice, reseed, generate) and
emits a VHDL package of expected values; if the input layout of the
hardware ever changes, that script is the only place to change it. A
third, \texttt{verifica\_top.py}, recomputes AES-CMAC from the same AES and
validates itself against RFC~4493 before checking anything.

Some of what the benches found deserves to be stated, because a
verification chapter that reports only passes has not verified much.

\paragraph{Ring model.} The LUT primitives used to simulate the ring
were first modeled with a strict unknown-propagation rule: any unknown
input gave an unknown output. At the start of a simulation every signal
is unknown, so the ring never left that state and never started. A real
NAND with its enable input at zero outputs one regardless of the other
input; the model now evaluates every combination compatible with the
known inputs and resolves the output when they all agree. Without this
the entire system-level bench would have been impossible.

\paragraph{I2C slave.} Two genuine design errors: the register pointer
did not advance on multi-byte writes, so consecutive bytes overwrote the
same address; and on reads the most significant bit was driven one clock
edge too late, shifting every byte. The first was fixed by incrementing
the pointer one state after the write strobe, so the address is still
valid during the strobe; the second by loading the shift register and
driving its first bit on the same falling edge that releases the
acknowledge. A third defect was in the bench itself: initializing the
register memory from the stimulus process created a second driver on the
same signal and every conflicting bit resolved to unknown. The slave is
the only door into the chip, so the bench was later extended with the bus
under abuse: spurious pulses shorter than the input filter in the middle
of a byte, on SDA with SCL high (a start followed by a stop, if not
filtered) and on SCL in its low phase; a stop and a repeated start in the
middle of a byte; bytes sent after a foreign address; the pointer
surviving a stop and wrapping at the end of the map; a master that
disappears with the clock stopped while the slave is holding SDA low in
its acknowledge; a master that issues a stop after acknowledging a read
byte, which \ac{I2C} itself makes impossible when the next byte starts
with a zero because the slave is holding the line; and the bus at
1~MHz and 100~kHz with a 20~MHz system clock. The bench counts the write
strobes to the register bank, so no aborted transaction may write, and a
property checked at every clock states that the slave never drives SDA
while idle. The bus-hang guard releases the line in the configured number
of cycles in both stuck cases, and nothing abnormal writes.

\paragraph{Health tests.} The ``healthy'' source of the first bench, a
shift register seeded with a single one, started with a run of 27 zeros
and a first window at 76\,\%; the detector fired. The detector was right.

\paragraph{Key leak through the random register.} The most serious
finding did not come from a bench but from reading the design again
before handing it over. The command that generated the key wrote the
full 256-bit output of the DRBG into the random-output register, which is
readable without the test pin; the first 128 of those bits \emph{were} the
key. The system bench even asserted that equality as a ``check''. The fix
separates the two: key generation leaves nothing readable, and a new
command fills the random register from an independent generation, after
the DRBG has updated its state. The bench now asserts the opposite, that
the register contains the key in neither half, and the Python
cross-check does the same.

\paragraph{Whole engine.} With the rings at their physical speed the
system bench, which drives almost a millisecond of I2C traffic, did not
finish in twenty minutes of CPU: every ring transition costs two random
draws in the jitter model. In that bench alone the stage delay is set ten
times larger, with the same relative jitter, and this is stated in the
bench. Its checks pass, and the key, the two challenges and their
tags are written to a file that \texttt{verifica\_top.py} checks: both
tags equal the CMAC recomputed by the independent Python AES, the
readable random-output register contains the key in neither of its
halves, and two generations give different keys. This is the first point at which a key born from
ring-oscillator noise, conditioned, generated and used to authenticate,
is confirmed by an implementation that shares nothing with the VHDL.
Several of the checks were added when three obligations that the
register map had placed on the host were moved into the hardware: a seed
command issued with the divider below its minimum is now refused, a
write to the divider register while a command is running is ignored, and
a divider value outside the admitted range is ignored and raises the
rejection bit of the diagnostic register. A
rule that only the documentation enforces is a rule that a careless host
breaks; the bench now exercises the three. The security rules of the
sequencer are also written as PSL properties inside the bench, checked
on every clock of the whole simulation rather than only at the steps
that provoke them: no generation and no seeding while an alarm is
raised, no seed collection before the start-up test, no generation with
the request counter exhausted, capture and seeding mutually exclusive
and capture only in test mode, the continuous stream never active while
a seed is collected and started only in test mode with the engine idle,
no authentication without a valid key, zeroization clearing the key in
the same cycle, and the engine never staying busy forever; cover
directives confirm that the bench
reaches the states those properties guard. A mutant of the sequencer
that drops the alarm check on key generation is caught both by the step
that expects the refusal and by the property. The bench also had to be
told to stop: with the rings running after reset, a simulation whose stimulus has
finished never runs out of events, and the first re-run consumed
forty-five minutes of CPU after its last check had passed.

\paragraph{Sampling window: an independent review.} After the divider
rules of November 2026 (rings of eleven and thirteen stages, a
divide-by-sixteen prescaler on the sampling ring, and a minimum, a reset
value and a maximum for the divider; Section~\ref{sec:ihp_ring11}) the
\ac{RTL} was reviewed by a separate session that was given the code and
the requirement, not the conclusions of the work. The requirement holds
\simu{}: the window between two samples is $2^{n}$ periods of the
sampling ring for the register value $n$ (\texttt{CFG\_KD},
$K_D = 2^{n}$), and nothing seeds below the minimum divider. But the
review found three defects of medium severity and one hole in the
benches. The meter firmware of Section~\ref{sec:lecturas_firmadas} wrote
a divider below the new minimum before seeding, so on the integrated
circuit it would never have seeded (it failed closed); it now seeds with
the reset value. A register value of 32 or more was truncated to five
bits, so 32 was taken as 0 without any flag; the whole byte is now
compared. And values from 0 to 3, below the prescaler, were accepted
while the real window was $2^{4}$; they are now refused. The hole was
that no bench measured the window: a mutant with half the window passed
the system bench. A new bench counts the periods of the sampling ring
between consecutive samples for every $n$ from 4 to 14 and checks the
refusals (47 checks), and the system bench gained the out-of-range
cases. The bitstream measured on the board predates these corrections
and differs from the corrected design only for out-of-range writes. What
the review left open is recorded for the physical implementation: there
is no timing constraint for the divided clock yet, and the first window
after a change of divider is shorter, which affects at most one bit.

\section{ESP32 verifier firmware}
\label{sec:firmware}

The firmware is an ESP-IDF~5 application for the classic ESP32 that
talks to the engine through the register map of Appendix~\ref{app:regs}
and offers a console over the UART. Its commands map onto the
verification plan: \texttt{id} reads identification and status;
\texttt{sembrar} and \texttt{generar} issue the long commands and poll
the busy flag, and after each one check the rejection bit, so that a
refused command is never taken for a quick one; in test mode
\texttt{generar} also reads the key, which is how the verifier is
provisioned; \texttt{reto N} performs $N$ challenge-response rounds
with nonces from \texttt{esp\_random()}, recomputing each tag with
\texttt{mbedtls\_cipher\_cmac} and counting matches and mismatches, the
mismatches being printed in full; \texttt{crudo N} dumps $N$ chunks of
raw bits and \texttt{esp N} dumps blocks of the ESP32's own generator, both
in the framed, CRC32-protected format of the ESP32 capture campaigns
(Section~\ref{sec:esp32_90b}), so that the same statistical pipeline
processes the two sources. The commands added for the board are
\texttt{kd}, which reads or writes the divider register and reports
whether the engine took the value; \texttt{flujo N}, which empties the
continuous stream of Section~\ref{sec:cdc} into numbered frames and
declares the string valid only if it arrived whole; \texttt{crudoq},
which captures a chunk like \texttt{crudo} but keeps the bus silent while
the capture lasts; \texttt{aleatorio N}, which dumps random blocks;
\texttt{borrar}, which clears the health alarms; and \texttt{cero}, the
zeroization. The time-outs follow the divider, since a seeding at a
large divider takes seconds. CMAC is
not enabled by default in the ESP-IDF build of mbedtls and is switched on
in the project defaults; the console runs at 115\,200~baud, the only rate
that proved reliable with the board's USB bridge in those campaigns,
and the log level is set to errors only so that log lines cannot corrupt
the frames. The register access layer (map, command issue, real-time
polling, rejection check) is a component shared with the application of
Section~\ref{sec:lecturas_firmadas}. The firmware builds without
warnings with ESP-IDF~5.3.2 on the author's machine and with 5.3.5 in the
continuous-integration workflow, and it is the firmware that drove the
engine on the board in every measurement of Section~\ref{sec:bringup} and
of Chapter~\ref{ch:ch7_results}.

One finding concerns the firmware as an instrument. An independent review
of the first night on the board noticed that every duration in the logs
was a multiple of 10~ms: the local build configuration had kept a 100~Hz
operating-system tick, and the 1~kHz of the project defaults had never
been applied. The access layer tolerates it, and no measurement was
affected except in that resolution: until 18 November 2026 the durations
reported by the verifier, and the ring frequencies derived from them,
are quantized to 10~ms, and they are quoted with that resolution; from
that date the tick is 1~ms.

Both firmwares are also exercised on the host, without a board: the
bench includes the firmware source unchanged, links it against a software
model of the engine that implements the register map as a second,
independent reading of the specification, and runs the sequence with the
same mbedtls~3.6.7 tree that ESP-IDF ships. The model's AES and CMAC
validate themselves against FIPS~197 and RFC~4493 before any check, so
that a model fault cannot pass for a firmware fault. The bench checks
counts, not just outcomes: that a rejected command is not mistaken for a
quick one, that a bus failure is counted as a bus failure and not as a
cryptographic mismatch, that nothing reaches the PC while an alarm is
raised, and that the timeouts last what they claim.

\section{The engine in a product: signed readings}
\label{sec:lecturas_firmadas}

The verifier judges the engine; a second firmware \emph{uses} it, as a
product would. The product is a generic energy meter on an ESP32-C3, the
RISC-V part of the small Wi-Fi devices, with the engine on the same
\ac{I2C} bus as the meter's own peripherals. Two uses, both fed by the
engine's entropy. First, the device generates its own ECDSA P-256 key
pair: mbedtls draws the private scalar through a callback that issues
one \texttt{aleatorio} command per 32-byte block, two blocks per key, and
the private key never leaves the chip; what leaves is the public key, or
a PKCS\#10 certificate request signed with it, which is what a device
would send to the manufacturer's CA so that nobody, the manufacturer
included, ever holds the private key. Second, every reading (device
identifier, sequence number, time, accumulated energy, power; 24~bytes)
is signed, so that whoever receives it checks integrity and origin
without trusting the transport or the offline store in between.

Three decisions carry the design. The key's strength is bounded by what
generated it: the engine's \ac{DRBG} is CTR\_DRBG with AES-128, 128~bits
of security, which is what P-256 offers, so a larger curve would gain
nothing from this seed. Signatures use deterministic ECDSA
(RFC~6979): the per-signature nonce is derived from the key and the
message, two signatures of the same reading are identical (the bench
checks it), and a poor generator at signing time cannot leak the key,
which is the classic ECDSA failure; the engine is therefore needed only
to \emph{create} the key, and a meter whose engine is in alarm keeps
signing with the key it has, while it cannot make a new one. And the
entropy callback fails closed: if the engine rejects the command
(unseeded, alarm, start-up test not passed) or the bus fails, mbedtls
aborts and no other source is substituted; a failed generation leaves the
previous key in service and never a half-made one. A monotonic sequence
number lets the receiver reject replayed readings, which a valid
signature alone does not.

The host bench runs the meter firmware against the engine model and
hands its console output to a PC script that verifies the frames with a
different library (\texttt{cryptography}, not mbedtls). The bench plants
one tampered reading (one bit of the energy field) and one replayed
reading among ten valid ones, and the script must find exactly those
two; the certificate request must parse, carry a valid self-signature and
the device's public key. All checks pass. The firmware builds with
ESP-IDF~5.3.5 for the ESP32-C3, and it also runs on Espressif's QEMU
emulation of that chip: without an engine every command fails closed, and
with the engine model linked into the firmware in place of the \ac{I2C}
driver (a build option, never for a board) the whole sequence runs on the
emulated RISC-V core with the target build of mbedtls, and the PC script
accepts its frames; the public key the emulated chip produces equals the
one the host bench produces from the same engine blocks.

The same build was then flashed onto a real ESP32-C3 module over
USB-serial and driven by a script that logs every line and times every
command. On the silicon, seeding the model takes tens of milliseconds,
generating the P-256 key and storing it takes about 0.17~s, a certificate
request 0.2~s and one signed reading about 0.2~s including the serial
round trip; the private key survives physical resets (the enable pin
pulsed from the serial adapter), the boot counter kept in flash advances
on each, the public key read back after a reset is unchanged and the
first reading of the next boot exceeds the last one of the previous boot
in sequence, so the anti-replay rule holds across real power cycles. Two
things the emulator could not show appeared at once. The console read its
commands with a buffered-line call over a non-blocking input, and over a
real USB-serial link the bytes of a command arrive with gaps: a single
command reached the firmware as four fragments, each rejected as unknown;
the console now accumulates characters up to the line end. And the new key
generated after forgetting the old one was identical to it, because the
engine model draws its ``randomness'' from a seedless pseudo-random
function that repeats the same sequence at every boot; this is not a
defect of the meter but the live demonstration of what the engine is for.
The PC verifier accepts every frame of the board log. The engine itself
has since run on a board with the verifier
(Section~\ref{sec:bringup}); what has not been done is to connect this
meter to the real engine: it has only run against the model, whose
entropy is an AES with a fixed seed, not a measurement.

\section{FPGA bring-up}
\label{sec:bringup}

% docs/decisiones_pendientes.md, results/basys3_o5_consola_*.txt,
% results/basys3_esquema, results/basys3_plano. Utilization and timing of the

% .bit there has the SHA-256 3affc2f5...9659 that docs/basys3.md gives for

The complete engine runs on a Digilent Basys~3 board, whose \ac{FPGA} is
an Artix-7 XC7A35T, with the ESP32 of Section~\ref{sec:firmware} on its
\ac{I2C} bus at 400~kHz (two wires and ground to a board connector, with
the pull-ups of the pins). A board switch is the test pin. This section
reports the implementation, the ring frequencies and the functional
result; the entropy campaign on the same board is in
Section~\ref{sec:campaign}. A first prototype had run a few days earlier
on the only board then at hand, a Basys~2, where only the entropy source
fits; what it taught is used below, and the two boards are compared in
Appendix~\ref{app:fpga}.

\paragraph{Flow and ring constraints.} The design is implemented with
Vivado~2025.2 on Linux, from a script and without a project, so that a
bitstream is reproduced by one command. The rings need four constraints,
known from the literature and from the vendor documentation:
\texttt{DONT\_TOUCH} on the cells of each ring (unlike \texttt{KEEP}, it
survives implementation), \texttt{ALLOW\_COMBINATORIAL\_LOOPS} on the nets
of each loop, \texttt{set\_disable\_timing} to break the loop for static
timing analysis, and one placement block per ring, apart from each other
and with the rest of the logic excluded, so that the rings are neither
merged nor placed side by side. The output of each ring is declared as a
clock. Two wrappers of the same engine are built: the normal one drives
the four-digit display with the ring frequency meter, and the
\emph{quiet} one has neither display nor meter and is the one closest to
the integrated circuit; every entropy measurement uses the quiet wrapper,
because the logic attached to the rings changes their phase noise
(Section~\ref{sec:campaign}).

\paragraph{Three things had to be fixed before the design met timing.}
First, the rings were not routed. Each placement block enclosed its ring
in two slices and also confined the routing; inside two slices there are
no tracks to close the loop, and ten connections were left unrouted. The
block now fixes only the placement. Second, the clock domain of the
sampling ring did not close at the real frequency. With five stages in
the sampling ring RO2 and seven in the sampled ring RO1, RO2 ran at
357.8~MHz \meas{}, and the critical path of its domain, from the sample
strobe of the \ac{ERO} to the write enable of the capture memory, takes
3.3 to 3.9~ns; with seven and nine stages RO2 still ran at 293~MHz
\meas{}. The board wrapper therefore uses eleven stages in RO2 and
thirteen in RO1. Third, the logic that closes the window of the
proportion test did not meet the 100~MHz system clock ($-0.26$~ns over
thirteen logic levels): it subtracted the count from the window size
before comparing. The two comparisons were rewritten against constants,
which is the same condition, and because this is a health test the
equivalence was not taken on trust: an independent review enumerated the
two conditions over 34\,236\,958 cases, co-simulated the old and the new
block with thirty sets of generics without a single difference, with two
mutants caught, and proved them equivalent formally for small generics
\simu{}.

\paragraph{A ring must be checked in the implemented netlist.} On the
Basys~2 the first bitstream had no rings at all: the tools had collapsed
the inverter chain, and it was found only by reading the implemented
netlist (Appendix~\ref{app:fpga}). On the Basys~3 the build script therefore
lists, after routing, every cell of both rings with its site and the
state of every net of the loop, and stops if the ring clocks do not exist
after synthesis. That listing showed something the constraints had not
prevented: Vivado had packed the inverters of RO2 two by two into the two
outputs of the same six-input \ac{LUT}, a placement optimization that
\texttt{DONT\_TOUCH} does not forbid, while RO1 was left alone. With one
\ac{LUT} per stage, each fixed to its site and to its position in the
slice, the same eleven-stage RO2 runs at 207~MHz instead of 130~MHz
\meas{} (Table~\ref{tab:ringfreq}). The fixed stage placement is the
default since 18 November 2026 and is the configuration of the final
bitstream; it fixes the \acp{LUT} of the rings, not the routing between
them nor the sampling flip-flop.

The frequencies are the first result and they were read before anything
else: a ring removed by the tools, or two rings locked to each other,
would otherwise be indistinguishable from a working source. Two readings
of the table matter later. The jump from 293 to 130~MHz does not follow
the stage count, which is how the merged inverters were found. And the
measured ratio of the two rings with fixed stages is 1.24, against
$13/11 = 1.18$ from the stage count: the routing between stages weighs as
much as the \acp{LUT}, so on an \ac{FPGA} the period of a ring has to be
measured, not derived.

\paragraph{The timing constraint of the sampling ring follows the
measurement.} A timing failure in the divider of the \ac{ERO} would look
like randomness, so the constraint on RO2 is not left as an estimate. It
is 4.5~ns, and for the quiet wrapper the script compares the longest
path of that domain with 0.9 times the measured period, 4.88~ns, and

\paragraph{The engine with the ESP32 as oracle (O5).} The functional
sequence was run in three sessions, on three different implementations:
17 November (free placement), 18 November (fixed stages) and 19 November
(final bitstream) \meas{}. In each one the verifier reads the
identification (complete engine, version 0x04, start-up test passed),
sets the divider, seeds --- the 512-bit seed is accepted only after its
proportion window closes clean ---, generates a key and reads it in test
mode, and runs twenty challenge-response rounds; then it zeroizes the
engine, checks that neither seed nor key remains, seeds and generates
again, obtains a different key, and runs twenty more rounds. In the
three sessions \textbf{the forty tags computed by the hardware equal the
forty that \texttt{mbedtls\_cipher\_cmac} computes on the ESP32}, with no
cryptographic mismatch and no bus error. The random blocks requested in
between arrive with a correct CRC (four per session in the first two).
The first two sessions seeded at \kd{16} (\texttt{CFG\_KD} $= 16$), the
working divider at the time; the third at \kd{19}, the divider that the
jitter measurement of Section~\ref{sec:campaign} requires, which is also
the minimum and the reset value of the final bitstream. That session
exercised the divider rules on the board: after configuration the
register reads 19; with \kd{18} the seed command is refused and the
rejection bit rises; with \kd{19} it is accepted; and writing 25, above
the maximum of the board wrapper, leaves the register at 19 and raises
the rejection bit.

What this run is, and what it is not, should be stated. It is the
integration of the \ac{FPGA} and the ESP32 with the ESP32 as an
independent judge of every tag, over a real bus, with keys born from the
noise of the rings. It is not a known-answer test on the board: the
register map offers no way to load a known key or a known seed, so the
official vectors are covered in simulation
(Section~\ref{sec:testbenches}) and not on the hardware. Nothing about
entropy follows from it either: a generator seeded with a constant would
pass the same forty rounds. That is the subject of
Section~\ref{sec:campaign}.
